# Підготовка до випуску після аудиту

Користувач доручив реалізувати доступні виправлення зі звіту від 1 листопада 2026 року. F01 (альтернативні наголоси) свідомо відкладено: словник, генерація відповідей та оцінювання не змінюються.

## Узгоджений напрям

Інкрементальні зміни поточної Room/outbox/Firebase архітектури. Повне переписування збільшило б обсяг неперевірених змін. Обмеження першого релізу лише гостьовим режимом також можливе, але користувач не просив прибирати наявні можливості.

- Оновити Billing 7.1.1 безпосередньо до стабільної 9.1.0: callback QueryProductDetailsResult, reconnect у SDK, одноразова buy-offer, pending і зрозумілі помилки. Ціна й offerToken мають походити з тієї самої пропозиції. Відновлення покупки — окрема дія; повторні перевірки не є новими покупками.
- Оновити й зафіксувати backend dependencies, прибрати відомі audit findings; перевірити фактичний API backend після оновлення.
- Release task із явними Gradle inputs, без захоплення script/project у task action; окремі production config/AdMob/signing/public URLs, зрозумілий перелік відсутніх значень. Жодних вигаданих production IDs або обходів перевірки.
- UMP керує дозволом на рекламні запити. До завершення читання Premium та consent стану реклама заблокована; після переходу у Premium або відкликання згоди завантажений ad відкидається. Застарілі callbacks не повертають його. Analytics/Crashlytics отримують незалежний добровільний перемикач, вимкнений до рішення користувача.
- Налаштування містять privacy policy, support, web account deletion request, privacy options і restore purchase. Публічні URL/email задаються конфігурацією; точний текст політики та завершення видалення потребують даних власника й рішення про billing retention.
- Некоректний cloud progress не перериває читання всіх коректних записів; UI не показує повний success, persistent retry не повторює незмінну помилку нескінченно. Некоректні записи не видаляються й не перезаписуються мовчки. Відновлення/адміністративна діагностика документуються.
- Pending reset має явний стан очікування. Захист generation та session commands зберігається. Повторний запит використовує наявний reset ID.
- Додати спостережуваність reminder failures, коректну telemetry показу ad і розмежування purchase/restore.
- Підготувати локальний verification script/CI та покроковий owner checklist із потрібними несекретними даними. Production deploy і публікація не виконуються без завершених конфігурацій.

## Перевірки

Збірка до/після, unit/Room/Compose regression tests, emulator rules та corrupted record сценарії, npm audit і backend tests, cache-compatible release-check (негативні та ізольовані fixture-перевірки), clean debug build, перевірка DEX/16КБ/merged Billing version. Native device, Play purchases, live Firebase, UMP geography/consent потребують пристрою й налаштованих зовнішніх ресурсів; їх статус документується окремо.

## Наступний етап: серверний запис прогресу

За повторним дорученням продовжено незалежну підготовку: debug Firebase конфігурацію відокремлено, додано read-only preflight та шаблон параметрів. Наявну CLI авторизацію використано лише для читання метаданих Firebase.

Для F09 обрано збереження поточної схеми документів і серверно валідований запис через `syncWordProgress`: Auth UID, App Check, bounded batch, перевірка всіх лічильників/сум, детерміноване per-device merge у транзакції, generation fence й rate limit. Серверна частина реалізована та перевірена unit/emulator тестами. Її підготовка не перемикає live клієнтів. Android transport, legacy migration і заборона старих direct writes потребують узгодженого cutover після відповіді про наявних користувачів/дані/APK; до цього відповідні чинні шляхи не змінюються.

Рекламна вікова модель й billing retention при видаленні також залишені як явні питання власнику. Незворотне видалення, платні ресурси, deploy або публікація документів не виконувалися.

## Завершення локального переходу після відповіді власника

Власник підтвердив: лише його тестові дані, інших користувачів/розданих APK немає. Android uploader і legacy migration тепер використовують callable; локальні rules відхиляють усі прямі word writes. Відповіді перевіряються до підтвердження outbox; late migration після reset/completion пропускається сервером. Схема, навчальні відповіді та наявні дані збережені. Live deployment та приймання Auth/App Check на пристрої залишаються окремим етапом, описаним у `docs/progress-server-cutover-2026-11-01.md`.
