## 2. Аудиторія, рейтинг і міжнародне поширення

1. Відкрити застосунок у Play Console → розділ App content / «Вміст застосунку» → Target audience and content.
2. Вказати фактичні групи **13–15, 16–17, 18+**, якщо застосунок дійсно адресований усім цим групам. Не обирати групи до 13 лише через бажаний рейтинг «3+».
3. Окремо заповнити IARC / Content rating. Рейтинг визначає анкета про фактичний контент; не підміняти відповіді заради певної цифри.
4. Вказати рекламу й покупки відповідно до фінальної збірки. Сам освітній характер не скасовує ці декларації.
5. У Countries/regions обрати всі потрібні доступні країни. Перевірити доступність одноразового товару й цін у тих самих країнах. «Усі країни» у консолі означає доступні для вашого акаунта території, а не гарантію однакової роботи всіх сервісів скрізь.
6. Для неповнолітніх погодити рекламний сценарій. Варіант: нейтральний локальний вибір вікової групи, без збирання точної дати народження; до вибору — без рекламних запитів; under-age параметри UMP і Mobile Ads для відповідних користувачів. Альтернатива — консервативна модель реклами для всієї аудиторії без персоналізації з належними віковими параметрами. Сам параметр «non-personalized ads» не замінює всі вікові та регіональні вимоги.
7. Після вибору я зможу завершити цей код і тести. Поточний UMP consent flow **ще не визначає вік**. Не випускати глобальну рекламну версію для 13+ із припущенням, що всі користувачі можуть самі погодитися на обробку даних. В окремих країнах поріг вищий за 13.

**Надати мені:** обрані age groups; рішення «локальний віковий екран» чи «консервативний режим для всіх»; чи залишаємо рекламу/діагностику для молодшої групи. Паролі не потрібні.

**Готово, коли:** декларації відповідають функціям; вікові сценарії реалізовані; UMP/Ads перевірено для молодшої, старшої й невідомої групи. [Google Play про цільову аудиторію](https://support.google.com/googleplay/android-developer/answer/9867159), [UMP: privacy](https://developers.google.com/admob/android/privacy).

## 3. Політика, підтримка і видалення даних

### 3.1. Рішення власника перед завершенням коду

Є [чернетка політики](legal/privacy-policy-draft.md) і [чернетка сторінки видалення](legal/account-deletion-draft.md). Їх не слід публікувати як остаточні документи: конкретні строки й процес ще не затверджені.

Потрібно визначити:

1. Хто обробляє запити: ви особисто через `wrocki.devoloper@gmail.com` чи автоматичний сервіс із підтримкою як резервом?
2. Строк відповіді й завершення видалення. Можна запропонувати до 30 днів, але це **пропозиція**, а не вже ухвалена обіцянка або універсальний правовий строк.
3. Чи видаляємо purchase token і зв’язок покупки з UID повністю? Це може ускладнити відновлення довічного Premium після повторної реєстрації. Чи потрібно зберігати мінімальні billing/anti-fraud записи? Якщо так — які саме, для чого, на який строк і на якій підставі. «Зберігати все назавжди» не є готовою політикою.
4. Строки для старих `epochs`, `resetRequests`, billing rate limits, diagnostic reports, листування підтримки, резервних копій. Вимкнення діагностики не видаляє автоматично все раніше передане до Google.
5. Як підтверджувати, що запит надсилає власник акаунта. UID чи звичайного листа з довільної адреси недостатньо. Бажаний шлях — повторна автентифікація Google; для зовнішнього запиту потрібне перевірене підтвердження контролю пов’язаної адреси/акаунта.

**Надати мені:** відповіді на ці п’ять пунктів. Не надсилати чужі персональні дані, Google ID tokens або purchase tokens.

### 3.2. Що потрібно доробити після рішення

Я зможу реалізувати серверний процес із перевіркою Auth/App Check/recent login, повторюваним безпечним виконанням і статусом завершення. Він має охопити:

1. Блокування нових записів у профіль на час видалення; запобігання відтворенню даних зі старого offline outbox або через Billing RTDN.
2. Видалення всіх вкладених даних `users/{uid}`: поточного й старих epochs, legacy progress, reset receipts, entitlements. Видалення тільки батьківського документа Firestore не видаляє subcollections.
3. Узгоджене опрацювання `purchaseTokens`, `billingRateLimits`, Firebase Auth та локальних даних пристрою. Сам `FirebaseAuth.delete()` цього не робить.
4. Відкликання сесій, перевірку залишків, обробку повторного запиту й збою посередині, підтвердження користувачу.
5. Наскрізний тест: створення акаунта → прогрес і покупка → видалення → старий токен/offline пристрій/RTDN не відтворюють акаунт → новий вхід має очікувану поведінку.

Не виконувати ручне «видалив users/{uid}, значить усе готово». Наявна кнопка в застосунку лише відкриває зовнішній шлях запиту. Вона **не означає**, що цей процес уже реалізовано. [Вимоги Google Play до видалення](https://support.google.com/googleplay/android-developer/answer/13327111).

### 3.3. Публічні сторінки без власного домену

Рекомендований для наявного Firebase варіант — Firebase Hosting з HTTPS на адресі, яку надає сервіс. Купувати домен для цих двох сторінок не обов’язково.

1. Повідомити production Firebase project ID та обраний Hosting site ID, якщо їх уже створено.
2. Після рішень із п. 3.1 я зможу перетворити чернетки на готові `privacy.html` і `delete-account.html`, додати конфігурацію Hosting та перевірити їх локально.
3. Перед публікацією перечитати конкретні зобов’язання. Переконатися, що поштова скринька реально приймає листи й запити опрацьовуються.
4. У Firebase CLI увійти у свій акаунт локально. Обирати **явний project ID** у кожному deploy; не запускати команду до перевірки готових сторінок.
5. Опублікувати тільки Hosting після погодження. Назви/команди для обраного сайту підготую разом із файлами; поточний `firebase.json` не змінено для випадкового deploy чернеток.
6. Перевірити обидва URL в інкогніто, на телефоні й без авторизації Google. На сторінці видалення має бути видимий спосіб надіслати запит, назва застосунку/розробника, перелік видалюваних і збережених даних та строки.
7. Передати мені **дві остаточні HTTPS-адреси**. Я внесу їх у конфігурацію збірки; ті самі URL треба вказати в Play Console.

**Готово, коли:** сторінки доступні всім, текст правдивий, шлях запиту працює, тестовий запит завершено до фактичного видалення. [Firebase Hosting quickstart](https://firebase.google.com/docs/hosting/quickstart).

## 4. Firebase: окремі development і production

1. У Firebase Console → Project settings → General записати **project ID** наявного проєкту й визначити його призначення. Якщо зараз усе в одному проєкті — створити окремий для development або production; не переносити/видаляти наявні дані навмання.
2. У кожному проєкті зареєструвати Android app із package **`com.intervalninaholosy.nmt`**.
3. Authentication → Sign-in method → увімкнути Google, обрати support email. Перевірити Web OAuth client; Android використовує його ID у Credential Manager.
4. Додати SHA-1 і SHA-256 правильних сертифікатів. Debug — локальний debug key. Для застосунку, встановленого з Play, потрібен **App signing certificate із Play Console**, який може відрізнятися від upload certificate. Після змін завантажити свіжий `google-services.json`.
5. Зберегти development JSON у `app/src/debug/google-services.json`, production — у `app/src/release/google-services.json`. Вони ігноруються Git. Не підміняти production тестовим JSON, щоб обійти перевірку.
6. Переконатися, що Firestore database `(default)` створена в обраному регіоні. Регіон існуючої бази не слід вважати довільно змінюваним; Functions зараз налаштовані на `europe-west1`.
7. Підготувати deployment rules/indexes у development. Перевірити `firestore.rules`, `firestore.indexes.json`; лише потім переносити на production із явно вказаним project ID. Правила з локальної папки самі в консолі не оновлюються.
8. App Check: development debug token зареєструвати тільки в dev-проєкті. Для release налаштувати Play Integrity. Подивитися метрики valid/invalid requests до enforcement для Firestore; callable Billing Functions уже вимагають App Check у коді.
9. Пройти Sign-In із development APK і з Play internal test. У разі помилки надати код/текст, версію APK і спосіб встановлення, а не credentials.

**Надати мені:** dev/prod project IDs, Firebase app ID, регіон Firestore, факт увімкнення Google provider, розташування JSON у локальному проєкті, публічні SHA відбитки, статус App Check. Приватний service-account JSON та debug App Check token у чат не потрібні.

**Готово, коли:** два проєкти розділені, вхід/синхронізація/покупки перевірені у правильних середовищах, production не приймає debug App Check credentials.

## 5. Google Play і сервер Premium

1. У Play Console створити/перевірити картку застосунку з package `com.intervalninaholosy.nmt`.
2. Перевірити merchant/payment profile. У Products / One-time products створити **`premium_remove_ads`** як одноразову довічну покупку. Не створювати замість неї subscription, rental чи preorder.
3. Активувати потрібну purchase option, встановити ціну й країни. Новий клієнт вибирає доступну звичайну buy-offer; ціна й токен беруться з однієї пропозиції. Валюта й локалізована ціна приходять із Play.
4. У Google Cloud увімкнути Google Play Android Developer API. Визначити service account, від імені якого реально працюють Functions. Надати йому в Play Console мінімальні права, необхідні для перевірки/підтвердження покупок цього застосунку. Не видавати всім Owner заради усунення помилки доступу.
5. Для Firebase Functions потрібен відповідний білінг-план і налаштовані квоти. Runtime у проєкті — Node 22. Залежності встановлювати за lockfile через `npm ci --ignore-scripts`.
6. Після локальних тестів розгорнути у development, потім у production Functions `verifyPremiumPurchase`, `refreshPremiumEntitlement`, `playPurchaseChanged`. Поточний codebase у `firebase.json` — `billing`, регіон — `europe-west1`. Я можу підготувати/перевірити конкретні команди після отримання project ID; live deploy у цій роботі не виконувався.
7. Налаштувати Pub/Sub topic **`play-billing`** у тому самому проєкті. Надати Google Play RTDN publisher доступ до цього topic; у Play Console вказати повний topic name. Відправити test notification і перевірити доставку/лог обробника. Не плутати test notification із перевіркою реального refund.
8. Додати власний тестовий Google-акаунт у license testers і до internal testing track. Установити застосунок **через посилання Play**, використовуючи той самий Play-акаунт.
9. Перевірити: успіх; скасування; pending із подальшим успіхом/відмовою; повторне відкриття; restore на другому пристрої; інший Firebase-акаунт; refund/revoke та RTDN; offline/мережеві помилки; заблоковану оплату. Новий Premium не має видаватися без серверної перевірки.

**Надати мені:** статус товару та purchase option, ціну/країни, email runtime service account (це ідентифікатор, не ключ), назву RTDN topic, результат test notification, посилання internal test, версію збірки та знеособлені помилки. **Не надсилати purchase token, токени входу або реквізити картки.**

**Готово, коли:** статус Premium коректно змінюється після покупки й refund на двох пристроях; гроші не списуються через наші ручні дії поза тестовою покупкою; користувач бачить зрозуміле відновлення. [Play Billing integration](https://developer.android.com/google/play/billing/integrate), [RTDN setup](https://developer.android.com/google/play/billing/getting-ready#configure-rtdn).

## 6. AdMob і рекламна приватність

**Це не системний дозвіл Android «дозволити рекламу».** UMP перевіряє, чи потрібне повідомлення про використання даних; форма з’являється лише за відповідного стану/регіону/налаштувань і попереднього вибору. Не додавався власний обов’язковий екран із питанням про рекламу кожному користувачеві. Для EEA/UK/Швейцарії є окремі вимоги Google до disclosures/consent; відсутність видимого запиту в іншому застосунку не визначає необхідну поведінку цього. [Пояснення Google для цих регіонів](https://developers.google.com/admob/android/privacy/gdpr).

1. У AdMob додати Android app для потрібного package та зв’язати з Play listing, коли це стане доступно.
2. Створити interstitial ad unit. Зберегти **App ID** з `~` і **Ad unit ID** з `/`. Це різні значення.
3. Privacy & messaging: створити/налаштувати повідомлення для потрібних регіонів і правил, указати остаточний privacy URL, опублікувати конфігурацію повідомлень.
4. Завершити вікову модель з розділу 2. UMP не вгадує вік користувача за віковим рейтингом сторінки Play.
5. Для тестування використовувати тестові ads/devices. У debug уже зафіксовані офіційні test IDs; не натискати власні live ads для перевірки.
6. Перевірити холодний запуск, відмову/згоду, privacy options, зміну рішення, перезапуск, offline, Premium і перехід у Premium під час завантаження реклами. Для перевірки регіонів потрібні debug-only UMP debug settings на тестовому пристрої; їх не переносити в release.
7. Перевірити фактичний мережевий трафік: до дозволеного стану AdManager не має ініціалізувати/завантажувати рекламу. `canRequestAds()` — рішення UMP; воно не завжди означає згоду на персоналізацію. Відмова може допускати обмежений режим за правилами SDK.
8. Налаштувати додатковий frequency cap у консолі за потреби. Доданий локальний ліміт 3 сесії / 3 хвилини прибрано за рішенням власника; налаштування консолі не змінювалися.

Тихі години й числовий frequency cap — **необов’язкові продуктові зміни**, а не вимоги production або Google. Тихі години обмежують лише навчальні сповіщення, не роботу застосунку чи реклами. Остаточне рішення власника: тихі години 00:00–07:00 залишити, локальний рекламний ліміт прибрати.

**Надати мені:** App ID, interstitial ID, статус повідомлень, обрану вікову модель, результати сценаріїв. Самі AdMob IDs не є паролями.

## 8. Data safety і моніторинг

1. Звірити [чернетку політики](legal/privacy-policy-draft.md) з реально увімкненими SDK/консолями. Не декларувати «дані не збираються»: є Auth, хмарний прогрес, billing, Ads, а за opt-in — Analytics/Crashlytics.
2. Для кожної категорії уточнити collected/shared, purpose, required/optional, encryption, retention і deletion. Вимкнений початково Analytics не означає його відсутності після згоди. SDK можуть передавати технічні ідентифікатори й діагностику незалежно від власних назв подій.
3. У Firebase/Google Cloud встановити бюджетні сповіщення на обрану суму й email, alerts на Functions errors/latency та проблеми RTDN. Бюджетний alert сам не вимикає витрати.
4. Перевірити фактичний `europe-west1` latency з цільових країн, читання/записи на сесію, затримку outbox та sync success. Кількість інсталяцій не дорівнює навантаженню.
5. У діагностиці розрізняти `premium_entitlement_verified`, дохід Google Play і фактичні `ad_shown`. Повторна перевірка Premium не є новим продажем.
6. Затвердити retention до запуску очищення старих epochs/reset receipts/billing записів. Без цього автоматичне видалення не додавалось.

**Надати мені:** заповнені категорії Data safety/знеособлений експорт або текст анкети, бюджет і адресата сповіщень, рішення щодо retention. Я зможу звірити декларації з кодом і підготувати конфігурацію моніторингу; факт доставки alerts треба перевірити у вашому проєкті.

## 10. Git, CI, залежності та залишковий контракт counters

### Git і CI

1. Визначити, де справжній репозиторій: у цій копії `.git` була порожньою. Якщо є інша робоча копія/історія — надати її шлях/remote; не створювати поверх неї нову історію.
2. Якщо історії справді немає, ініціалізувати Git у корені, перевірити `.gitignore`, переглянути список staged files. Не додавати ключі, local properties, service-account JSON, `.local-verification` чи credentials.
3. Обрати приватний remote, налаштувати власні author name/email. Перед першим push перевірити список файлів і secret scan.
4. Доданий `.github/workflows/verify.yml` запускає Android build/tests/lint/APK check, Node 22 tests/audit та demo Firestore tests. Це підготовлений workflow; **його виконання в GitHub ще не перевірено**, оскільки remote не підключений.
5. Увімкнути required checks після першого успішного workflow. Релізні secrets/підпис не потрібні цьому debug CI. Немає automatic deploy/publish.
6. Локальна команда: `powershell -File scripts/verify-local.ps1 -Emulators`; за потреби чистої збірки додати `-Clean`. Для backend потрібен Node 22, для Android — сумісний JDK/SDK. Локально перевірений runtime Node 22.23.4; системний Node 24 не підмінявся.

**Надати мені:** remote URL або шлях до наявного репозиторію, обраний author name/email, помилки першого CI. Паролі GitHub і PAT у чат не потрібні.

### Залишкові npm findings

Оновлено до `firebase-admin 14.5.0`, `firebase-functions 7.4.0`, `googleapis 189.0.0`. Остаточний audit: **0 high/critical, 6 moderate**. Ланцюжок включає `google-gax/gaxios → rimraf 5 → glob 10.5.0 → minimatch 9.0.9`. `npm audit fix` не усунув його; доступного виправлення в тій самій major-лінії glob 10 під час перевірки не знайдено.

1. Не запускати автоматично `npm audit fix --force` у production.
2. Перед deploy повторити `npm audit --omit=dev --prefix functions`; зберегти новий результат.
3. Обрати оновлення upstream SDK, коли воно прибере ланцюжок, або окремо протестувати scoped overrides/зміну transport dependency. Major override не додано без доказів сумісності.
4. Поточні findings стосуються filesystem glob/DoS; зовнішній purchase token у нашому коді не передається як glob pattern. Це зменшує очевидну досяжність, але **не доводить відсутності ризику всередині залежностей**.
5. CI блокує high/critical. Moderate залишаються видимими й потребують задокументованого рішення перед production backend.

**Дані від власника для дослідження не потрібні.** Повне закриття залежить від перевіреного сумісного оновлення або окремого випробування overrides у staging. Не позначати цей пункт «audit clean».

### Firestore counters

Клієнт тепер перевіряє цілі невід’ємні counters, формат і суми. При пошкодженні застосовує коректні документи, не просуває checkpoint, не затирає проблемні записи й не повторює той самий WorkManager retry без кінця. Після ремонту даних ручний sync відновлює роботу; це перевірено Room-тестом.

Серверний контракт тепер реалізований: `syncWordProgress` перевіряє всі counters й суми, клієнт використовує callable, локальні rules забороняють direct word writes. Користувач підтвердив, що є лише його тестові дані; повторно питати про наявних користувачів не потрібно.

1. Для завершення увімкнути Cloud Functions API у dev, перевірити тарифний план та App Check, під’єднати телефон. Детальні кроки й команди: [перехід на серверний запис](progress-server-cutover-2026-11-01.md).
2. Розгортати в порядку callable → новий APK/перевірка → rules; повторити перевірку після правил. До deployment callable новий uploader не може синхронізувати, але зберігає outbox.
3. Якщо вже є помилка: не очищати базу й не перевстановлювати застосунок із невідправленими відповідями. Записати версію/час/сценарій, звернутися до підтримки. Адміністратор має перевірити дані у своєму захищеному середовищі й виправити за резервною копією; UID сам по собі не є дозволом на видалення.

**Надати мені:** стан Cloud Functions API і тарифного плану, модель/Android version підключеного пристрою, факт локальної реєстрації dev App Check debug token. Сам токен і сирі профілі не надсилати.
